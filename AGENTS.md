# AGENTS — правила работы с проектом G10 Киров

Дата актуализации: 19 августа 2026 года.

## Обязательный контекст

- Работать только с лендингом G10 для Кирова.
- Приоритет источников: канонический бриф → актуальная папка исходников → утверждённые решения заказчика.
- Екатеринбург — только функциональный референс. Не переносить его дизайн, тексты, случайные фото или виджеты.
- Не добавлять неподтверждённые факты, портреты, цены и расписание; черновые строки с `???` не публиковать.
- Готовый banner JPEG считать атомарным изображением: не накладывать на него DOM-текст, вращение, блики или crop без отдельного решения.

## Технические правила

- Проект статический: редактировать `index.html`, `styles.css`, `script.js` и Vercel Function в `api/` без внедрения фреймворка или сборщика.
- Сохранять текущую семантику, адаптивность, focus states, reduced-motion и cookie consent.
- Формы отправляются на `/api/submit-application`; не имитировать успешную отправку, если production env не настроены.
- Секреты не помещать в HTML, CSS, JavaScript, Markdown, Git или архив. `.env.local` остаётся локальным и игнорируется Git.
- После согласованного изменения runtime проверять локальный проект и вручную публиковать актуальную версию на Vercel. Для docs-only изменений деплой не нужен.
- Не считать production backend активным без подтверждённой тестовой доставки заявки.

## Документация

После изменения проекта сверять и при необходимости обновлять:

- `PROJECT.md` — краткий источник истины по стеку, структуре и production;
- `PROJECT_CONTEXT.md` — подробный технический контекст;
- `CURRENT_TASK.md` — текущий статус и следующий порядок работы;
- `TODO.md` — чек-лист;
- `HANDOFF.md` и `NEW_CHAT_CONTEXT.md` — передача в новый чат;
- `CONTENT_MAP.md`, `MATERIALS_INDEX.md`, `MISSING_MATERIALS.md`, `IMPLEMENTATION_PLAN.md` — требования, материалы, риски и план.

В документах указывать дату актуализации и различать `[FACT]`, `[INFERENCE]`, `[ASSUMPTION]` и `[UNKNOWN]`, если статус не подтверждён.

## Git и проверка

- Не выполнять `git reset --hard`, `git checkout --` и другие destructive-команды.
- Перед передачей проверить `node --check script.js`, `node --check api/submit-application.js` и `git diff --check`.
- При изменении frontend проверить desktop/mobile, отсутствие горизонтального overflow, формы, dialogs и консоль браузера.
- Не коммитить незапрошенные изменения и не публиковать локальные секреты.

## Стиль объяснений для пользователя

- Пользователь не программист и может не знать технический сленг.
- Не использовать без объяснения термины `hash`, `commit`, `branch`, `CLI`, `SSH`, `public key`, `API`, `DNS`, `nginx`, `FTP`, `FTPS`, `SFTP`, `deployment` и другие сокращения.
- При первом употреблении любого технического термина сначала объяснить простыми словами: что это такое, зачем это нужно именно в текущей задаче и какое действие требуется от пользователя.
- Ошибки вроде `Permission denied (publickey)` переводить на понятный русский язык: например, «GitHub не пустил компьютер, потому что для него не настроено подтверждение доступа».
- Не сообщать только хеши, команды или коды ошибок без расшифровки. Техническое значение можно указать в скобках после понятного объяснения.
- В инструкциях явно разделять: что сделал Codex, что должен сделать пользователь и какой результат ожидается.
- Не просить пользователя вводить пароли, приватные ключи или токены в чат. Объяснять безопасный способ настройки доступа.
